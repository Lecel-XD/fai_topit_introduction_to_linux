# Ответы на вопросы и задания

> **1\. Зачем при создании SSH-ключа предлагается задать парольную фразу и от какой угрозы она защищает?**
Парольная фраза шифрует файл приватного ключа на диске. Если файл ключа не зашифрован и попадёт к злоумышленнику, тот сможет сразу подключиться к серверу. Если парольная фраза установлена, то без её знания файл ключа бесполезен. Защищает при краже или утечке ключа.

> **2\. Зачем при первом подключении по SSH клиент показывает отпечаток ключа сервера и просит подтвердить его? Что произойдёт, если отпечаток изменится?**
Отпечаток ключа сервера — это хеш ключа хоста. Он нужен, чтобы пользователь мог проверить, подключается ли он к нужному серверу или нет. При первом подключении ключ хоста запоминается в файле, при последующих сверяется автоматически. Если отпечаток изменится, то есть вероятность, что злоумышленник пытается выдать себя за сервер, и клиент откажется подключаться. При этом отпечаток ключа может измениться и сам по себе при переустановке сервера, пересоздании ключей хоста (удаление /etc/ssh/ssh_host_* и перезапуск sshd)

> **3\. Если у двух пользователей одинаковые пароли, можно ли понять это по /etc/shadow? Почему?**
Нет, одинаковые пароли не дают одинаковых хешей. При сохранении хэша пароля к нему добавляется соль - случайная строка, уникальная для каждого пользователя. Она объединяется с паролем, и только после этого результат прогоняется через хэш-функцию. Поскольку соли у двух пользователей разные, даже при одинаковых паролях хеши получатся разными. Соль хранится рядом с хешем в /etc/shadow.

> **4\. Заполните таблицу: атрибут (r, w, x, suid, sgid, sticky bit), сокращённое название, значение для файла, значение для каталога. В таблице должно быть 6 строк.**
> | Атрибут | Сокращённое название | Значение для файла | Значение для каталога |
> |---|---|---|---|
> | r | read | Читать содержимое файла | Просматривать содержимое каталога (ls) |
> | w | write | Редактировать файл, писать в него | Изменять таблицу каталога: создавать, удалять и переименовывать записи. Не даёт права менять содержимое самих файлов — для этого нужно w на файле |
> | x | execute | Запускать файл, как программу / скрипт | Делать его текущим каталогом (cd). Даёт доступ к файлам внутри по имени |
> | suid | set user id | При запуске процесс получает права владельца файла | Игнорируется |
> | sgid | set group id | При запуске процесс получает права группы файла | Новые файлы в каталоге наследуют группу каталога, а не группу создателя |
> | sticky | sticky bit | Сейчас ничего не делает. Раньше такой файл не выгружался из ОЗУ | Удалять / переименовывать файл может только владелец файла, владелец каталога и root |

> **5\. Почему для удаления файла нужны права на каталог, а не на файл? Какие изменения вносит установка sticky bit на каталог?**
Потому что каталог - это табличка с записями вида ("Имя", "inode"). В ней хранятся все содержащиеся в каталоге названия файлов. Удаление файла - это операция над каталогом: удаляется запись в таблице, а не содержимое файла. Поэтому для удаления нужны права w и x на каталог. Sticky bit меняет правила игры: удалять/переименовывать файл может только владелец файла, владелец каталога или root.

> **7\. Чем различаются su, su \- и sudo? Почему в Debian для повседневной работы рекомендуют sudo, а не пароль root?**
> - ```su``` переключает на другого пользователя (по умолчанию root), сохраняя текущее окружение. Требует пароль целевого пользователя. 
> - ```su -``` то же самое, но ставит окружение целевого пользователя.
> - ```sudo``` Выполняет одну команду от имени другого пользователя, не переключая сессию. Требует пароль своего пользователя.
> 
> В Debian для повседневной работы рекомендуют sudo, а не пароль root, так как sudo безопаснее. Если пароль root'а сольют, то компрометируется всё. Также sudo выдаёт права точечно: можно разрешить конкретные команды, а не полный доступ.

> **8\. Почему правила с подстановочными знаками в sudoers считаются опасными?**
Чаще всего такие права разрешают неочевидные на первый взгляд команды. К примеру, с правами ```user ALL = /bin/nano /etc/nginx/*```  пользователь может выполнить ```sudo nano /etc/nginx/../../etc/shadow``` и прочитать хэши паролей. Поэтому в sudoers следует придерживаться принципа наименьших привилегий: запрещать всё и точечно разрешать конкретные команды с фиксированными аргументами.

> **9\. Чем отличается SIGTERM от SIGKILL? Какой из них процесс может перехватить?**
SIGTERM "просит" процесс завершится. При этом его можно перехватить и обработать: процесс может корректно завершиться, сохранить данные и т.п. SIGKILL же в свою очередь завершает процесс мгновенно, его нельзя перехватить или проигнорировать.

> **10\. Что происходит с процессом, запущенным через &, при закрытии SSH-сессии, и почему nohup меняет это поведение? Почему у процесса с nohup PPID после этого стал другим?**
Процесс, запущенный через &, работает в фоне и привязывается к терминалу. При закрытии SSH-сессии терминал тоже закрывается, и ядро посылает всем процессам, привязанным к этому терминалу, сигнал SIGHUP, который по умолчанию завершает процессы с &. nohup же игнорирует SIGHUP и процессы не завершаются. PPID меняется, так как после закрытия SSH-сессии процесс остается без PPID и ядро переподвешивает его к процессу init (PID 1).

> **11\. Что такое зомби-процесс? Можно ли его убить командой kill \-9 и почему?**
Это процесс, который завершился, но родитель ещё не прочитал его код возврата. Его нельзя убить через kill \-9. Сигналы доставляются процессу, а зомби - просто запись в таблице процессов, которую держит ядро для родителя. Ядро игнорирует сигналы, адресованные зомби.

> **12\. Чем отличается вывод sshd \-T от строк, найденных в sshd\_config через grep? Приведите пример параметра, у которого они различаются.**
grep по sshd_config показывает сырые строки файла, выводит закомментированные строки, не учитывает вложенные файлы и приоритеты. sshd -T показывает действующую итоговую конфигурацию, подставляя значения по умолчанию и параметры из других конфигурационных файлов. К примеру, PasswordAuthentication может быть указан в sshd_config.d/*.conf и отсутствовать в основном sshd_config. grep не выведет это свойство, а sshd -T покажет.

> **13\. Какой риск возникает, если владельцем исполняемого файла будет root и на этот файл будет установлен suid?**
Такой файл при запуске получит права root. Если пользователь имеет права на запись в файл, он может вписать туда, к примеру, запуск /bin/bash и получить root-shell
